Authorization gateway for voice agents

Nothing said on a call can open a protected action.

Anticlus sits between your AI voice agent and the actions it can take: changing a supplier's bank account, releasing a payment, changing contact details.

Read the quickstart Book a call

For companies deploying voice agents with real permissions (finance operations, banks, insurers, telecoms, BPO call centres) and for the developers building those agents.

The problem

A voice agent with permissions can be talked into using them

Voice agents now do more than answer questions. Some can change a supplier's bank account, release a payment or change contact details.

  • Everything on a call comes from the caller

    The name, the reason and the new number or IBAN are all supplied by the person on the line. So is the voice.

  • The agent that listens is the agent that acts

    If the agent holds the keys to a protected action, persuading the agent is enough to open it.

  • Checking with details given on the call checks nothing

    A confirmation sent to a number or address the caller just provided goes back to the caller.

How it works

The agent asks, the gateway decides, the tool checks the grant

Anticlus stands between the voice agent and the protected tool. Verification goes through the MFA system your company already runs.

  1. The agent asks before each protected action

    Before it changes a bank account, releases a payment or changes contact details, the agent asks the gateway.

  2. The gateway scores the call and checks the caller

    It scores the call for social-engineering signals and checks the caller against what is on file. It answers allow, verify first, deny, or escalate to a human.

  3. Verification goes to your existing MFA

    On "verify first" it sends a signed challenge to your existing MFA system: a banking-app push, a one-time code, or a callback to the number on file. It never uses contact details given during the call.

  4. A single-use grant, bound to the exact action

    On allow it issues a single-use grant bound to that exact action and its exact parameters. The protected tool refuses to run without it. A verification for one bank account never opens another.

What stays out of reach

  • The agent never holds the keys. It cannot record a verification or consume a grant.
  • The caller never hears a score or a rule.
  • Every decision lands in an audit trail that holds no transcript and no parameter values, only a hash.

How you integrate it

  • An HTTP API.
  • A Python client.
  • An MCP proxy mode that puts the gateway in front of an existing MCP server without changing it.

A real run

One call, from request to refused replay

An excerpt of a run. The caller asks to change a supplier's bank account.

run excerpt
callerHello, Sophie Maes from Acme Industrial. We are moving to a new bank.
gatewaydecision: verify_first[1]
agentBefore I can do that, I'll confirm it with Acme Industrial NV using the contact details we already have on file.[2]
toolupdate_supplier_iban -> REFUSED (no grant)[3]
mfathe contact on file approved
gatewaydecision: allow[4]
toolupdate_supplier_iban -> DONE (verified by app)
toolsame grant again -> REFUSED (used)[5]
  1. The gateway answers "verify first". The caller hears no score and no rule.
  2. The agent says only that it will confirm with the contact already on file. The challenge never goes to details given during the call.
  3. Until a grant exists, the protected tool refuses to run.
  4. After the contact on file approves, the gateway allows the action and issues a grant bound to that exact action and its exact parameters.
  5. The grant is single-use. Presenting it a second time is refused.

The benchmark

A public benchmark that measures one thing

The benchmark pairs scam calls with legitimate calls, in English and French, in text and audio. It measures whether the protected action runs.

Results are published in the repository. That includes false refusals: the legitimate calls the gateway turned away.

Why the name
